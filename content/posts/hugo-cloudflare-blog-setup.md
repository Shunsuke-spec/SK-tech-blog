## 1. 技術ブログを始めた目的

### 1-1. 日々の技術経験を資産として残す

普段の業務では、AWS、Azure、Windows Server、ネットワークなど、さまざまな技術に触れています。トラブル対応では、原因を調査して解決できたとしても、時間が経つと詳細を忘れてしまうことがあります。

そこで、次の内容を記録しておくことにしました。

- 発生した事象
- 調査した内容
- 実際に使用したコマンド
- 原因と解決方法
- 調査から得られた学び

単なる作業メモではなく、後から読み返して再利用できる技術資料として蓄積していきます。

> **クリス**：作業メモじゃダメなんですか？
>
> **タマキ先生**：メモは書いた本人がその場の文脈を覚えているうちしか読めないことが多いんだ。「何が起きて、何を調べて、なぜそれが原因だったのか」まで書いておくと、半年後の自分にも、他の人にも使える資料になるよ。

### 1-2. 転職・キャリア形成に活用する

もう一つの目的は、自分の技術力を客観的に示すことです。

職務経歴書に「AWS運用経験あり」「Azureのトラブル対応経験あり」と書いても、どの程度の知識や経験があるのかは伝わりにくいことがあります。実際の調査内容や原因の切り分けの過程を記事として公開すれば、業務経験や技術的な考え方を具体的に示せます。

将来的には、転職活動やフリーランスとしての案件獲得にも活用したいと考えています。

> **クリス**：経歴書の一行より、記事の方が伝わるものですか？
>
> **タマキ先生**：「経験あり」は誰でも書けるけど、トラブルをどう切り分けたかは、実際にやった人にしか書けないからね。考え方の筋道が見えるのが、記事のいちばんの強みだよ。

### 1-3. 同じ問題で困っている人の役に立つ

IT業務では、エラーが発生したときにインターネット上の技術記事に助けられることがよくあります。自分が経験したトラブルや解決方法も、同じ問題に遭遇した誰かの参考になるかもしれません。

そのため、できるだけ具体的な事象と調査手順を残すことを意識します。ただし、業務で知り得た顧客情報や機密情報は公開せず、必要に応じて構成や設定値を一般化します。

### 1-4. AIを活用して継続的に記事を作成する

技術ブログを続けるうえで、記事作成に時間がかかることは課題になります。そこで、ChatGPTを活用して、技術メモから記事の構成案やMarkdownを作成する運用を考えました。

基本的な流れは次のとおりです。

1. 業務で経験したトラブルや学びをメモする
2. ChatGPTで記事の構成と文章を整理する
3. 技術的な正確性と機密情報の有無を確認する
4. Markdown形式で保存する
5. GitHubへPushして公開する

> **クリス**：AIに書かせたら、全部おまかせでいいんじゃないですか？
>
> **タマキ先生**：文章を整えるのはAIが得意だけど、AIはメモにない原因を「それらしく」補ってしまうこともあるし、メモに混ざった顧客名やIPアドレスをそのまま記事に入れてしまうこともある。だから**3番の確認は自分でやる**。ここだけは人の仕事だね。

## 2. ブログのシステム構成

このブログは、Hugo・Git・GitHub・Cloudflare Pagesを組み合わせた静的サイトです。

### 2-1. 全体構成

```text
自分のPC（Windows）
  Hugo：Markdownで記事を作成・編集
      │
      │ git push
      ▼
GitHub
  記事・設定・テーマを保存（ソースコード管理）
      │
      │ Pushを検知
      ▼
Cloudflare Pages
  Hugoで静的HTMLを生成 → 自動デプロイ → HTTPSで配信
      │
      ▼
インターネット
  誰でも閲覧可能
```

### 2-2. 採用した技術

| 技術 | 役割 |
|---|---|
| Hugo | Markdownから静的HTMLを生成 |
| PaperMod | ブログのデザインテーマ |
| Git | ファイルの変更履歴を管理 |
| GitHub | ソースコードを保存・管理 |
| Cloudflare Pages | ビルド・デプロイ・Webサイト配信 |

Hugoは**静的サイトジェネレーター（SSG）**です。Markdownファイルをもとに、あらかじめHTMLを生成しておくため、WordPressのようなPHPやデータベースを必要としません。また、Cloudflare Pagesを利用することで、自分でWebサーバーを構築・運用する必要もありません。

> **クリス**：「静的」って、どういう意味ですか？
>
> **タマキ先生**：アクセスがあるたびにページを組み立てるのではなく、**ページを先に全部作っておいて、それをそのまま渡す**ということ。WordPressはアクセスのたびにPHPがデータベースから記事を読んでページを作るけど、Hugoは公開前にHTMLを作り終えている。だから仕組みがシンプルなんだ。

### 2-3. なぜこの構成を選んだのか

**① 運用コストを抑えられる**

小規模な個人ブログであれば、GitHubやCloudflare Pagesの無料枠で運用できます。

**② サーバー管理が不要**

OSのパッチ適用やWebサーバーの保守などを自分で行う必要がありません。

**③ セキュリティ上の攻撃対象が少ない**

静的HTMLを配信する構成なので、CMSの管理画面やデータベースを狙う攻撃など、一部のリスクを避けられます。ただし、GitHub・Cloudflareアカウントへの不正アクセス、依存ライブラリ、公開情報の漏えいなどには注意が必要です。

**④ GitやCI/CDの学習にもなる**

GitHubに変更をPushすると、Cloudflare Pagesが自動的にビルド・デプロイを行います。小規模ながら、Gitによるソース管理と自動デプロイを実践できる構成です。

> **クリス**：インフラエンジニアなら、自分でWebサーバーを立てた方が勉強になりませんか？
>
> **タマキ先生**：それも一つの考え方だね。でも、このブログの目的は「記事を書き続けること」。サーバーの保守に時間を取られて記事が止まったら本末転倒だから、運用の手間がかからない構成を選んだんだ。それでもGitやCI/CDには自然に触れられるのが、この構成のいいところだよ。

## 3. ローカル環境とGitHubリポジトリ

### 3-1. ローカルの保存場所

Windows上では、ユーザーの「ドキュメント」フォルダの下にブログを配置しています。PowerShellで移動する場合は、次を実行します。

```powershell
cd $HOME\Documents\shun-tech-blog
```

`$HOME` は、PowerShellでログイン中のユーザーのホームフォルダ（`C:\Users\<ユーザー名>`）を表します。

### 3-2. GitHubリポジトリ

GitHubでは、次のリポジトリを使用しています。

https://github.com/Shunsuke-spec/SK-tech-blog

記事のMarkdown、Hugoの設定、PaperModテーマのサブモジュール情報などを管理しています。

### 3-3. ブログのURL

公開先は次のとおりです。Cloudflare PagesによりHTTPSで配信されます。

https://sk-tech-blog.pages.dev/

## 4. ディレクトリ構成

Hugoのプロジェクトは、おおむね次の構成です。

```text
shun-tech-blog/
├── archetypes/
├── content/
│   └── posts/
│       ├── first-post.md
│       └── azure-rdp-license.md
├── themes/
│   └── PaperMod/
├── static/
├── hugo.toml
└── .gitmodules
```

| ファイル・フォルダ | 説明 |
|---|---|
| `archetypes/` | `hugo new` で記事を作るときのひな形 |
| `content/posts/` | ブログ記事の保存場所 |
| `themes/PaperMod/` | デザインテーマ |
| `static/` | 画像などの静的ファイル |
| `hugo.toml` | Hugoの設定ファイル |
| `.gitmodules` | Gitサブモジュールの設定 |

基本的には、`content/posts/` にMarkdownファイルを追加することで記事を増やせます。

> **クリス**：テーマが「サブモジュール」になっているのはなぜですか？
>
> **タマキ先生**：PaperModは別の人が開発しているリポジトリだよね。それを丸ごとコピーするのではなく、「このリポジトリのこのバージョンを使う」という参照だけを持っておくのがサブモジュール。テーマの更新を取り込みやすくなるし、自分のリポジトリもすっきりするんだ。

## 5. Hugoの設定

ブログの基本設定は `hugo.toml` で管理しています。設定例は次のとおりです。

```toml
baseURL = "https://sk-tech-blog.pages.dev/"
title = "Shun Tech Notes"
theme = "PaperMod"

[pagination]
  pagerSize = 10

[params]
  defaultTheme = "auto"
  ShowReadingTime = true
  showtoc = true
  tocopen = false
```

- `baseURL`：ブログの公開URL
- `title`：ブログのタイトル
- `theme`：使用するテーマ
- `pagerSize`：一覧ページに表示する記事数
- `defaultTheme`：画面テーマ（ライト・ダーク）の初期設定
- `ShowReadingTime`：記事の推定読了時間を表示
- `showtoc`：目次を表示
- `tocopen`：目次を最初から開いておくか

※上記は設定例です。実際のファイルは必要に応じて確認します。

## 6. 新しい記事を作成する方法

ここからは、実際に記事を公開する手順です。

### STEP 1：プロジェクトに移動

```powershell
cd $HOME\Documents\shun-tech-blog
```

### STEP 2：新しい記事を作成

例として、AzureのRDPトラブルに関する記事を作成します。

```powershell
hugo new content content/posts/azure-rdp-license.md
```

これにより、`archetypes/` のひな形をもとに、次のファイルが作成されます。

```text
content/posts/azure-rdp-license.md
```

※同名のファイルがすでにある場合は、新規作成せず既存ファイルを編集します。

### STEP 3：記事を編集

作成したMarkdownファイルを、VS Codeやメモ帳で編集します。

```markdown
---
title: "Azure VM複製後にRDP接続できなかった話"
date: 2026-10-10T06:00:00+09:00
draft: false
tags: ["Azure", "RDP", "Windows Server"]
---

## 概要

Azure VMの複製後にRDP接続できない事象が発生しました。

## 調査

3389番ポートの疎通を確認しました。

## 解決方法

管理用RDP接続を使用しました。

## まとめ

Pingが通らなくても、サーバが停止しているとは限りません。
```

ここで重要なのが次の一行です。

```yaml
draft: false
```

> **クリス**：`draft` って、そんなに大事なんですか？
>
> **タマキ先生**：`draft: true` だと「下書き」扱いになって、通常の公開ビルドでは記事が出力されないんだ。しかも `hugo new` で作ったファイルは、ひな形の設定によっては最初から `draft = true` になっていることが多い。**Pushしたのに記事が出てこない**ときは、まずここを疑うといいよ。

### STEP 4：ローカル環境で表示確認

次のコマンドでHugoの開発サーバーを起動します。

```powershell
hugo server -D
```

ブラウザで `http://localhost:1313/` にアクセスすると、記事のレイアウトや内容を確認できます。`-D` は下書き記事も表示するオプションです。確認が終わったら、PowerShellで `Ctrl + C` を押して停止します。

> **クリス**：`-D` を付けて確認したら、下書きのまま気づかずに公開しちゃいそうです。
>
> **タマキ先生**：鋭いね。`-D` 付きだと下書きも表示されるから、ローカルでは見えるのに本番には出てこない、ということが起こる。公開前の最終確認では、`-D` なしで起動して記事が表示されるかを見ておくと安心だよ。

## 7. GitHubへアップロードする方法

記事の編集が終わったら、Gitを使ってGitHubへ反映させます。

### STEP 1：変更内容の確認

```powershell
git status
```

追加・変更されたファイルを確認します。

### STEP 2：記事をステージング

```powershell
git add content/posts/azure-rdp-license.md
```

`git add` は、次のコミットに含めるファイルを指定するコマンドです。

### STEP 3：コミット

```powershell
git commit -m "docs: add Azure RDP troubleshooting article"
```

コミットは、変更内容をGitの履歴として記録する操作です。`-m` の後ろには、変更内容を説明するメッセージを指定します。

### STEP 4：GitHubへPush

```powershell
git push
```

これで、ローカルで記録したコミットがGitHubへ送信されます。

> **クリス**：コミットしたら、もうGitHubに上がっているんじゃないんですか？
>
> **タマキ先生**：よくある勘違いだね。コミットは**自分のPCの中に履歴を記録するだけ**。GitHubに送るには `git push` が必要なんだ。「コミットはセーブ、プッシュはアップロード」と覚えるとわかりやすいよ。

## 8. Cloudflare Pagesによる自動デプロイ

GitHubの `main` ブランチへPushすると、Cloudflare Pagesが変更を検知し、次の処理を自動で実行します。

1. GitHubからソースコードを取得
2. PaperModテーマなどの依存ファイル（サブモジュール）を取得
3. HugoでMarkdownをHTMLへ変換
4. 生成されたファイルをCloudflare Pagesへ配置
5. 公開サイトを更新

基本的なビルド設定は次のとおりです。

| 設定項目 | 設定値 |
|---|---|
| Framework preset | Hugo |
| Build command | `hugo` |
| Build output directory | `public` |
| Root directory | 空欄 |
| 環境変数 `HUGO_VERSION` | `0.152.2` |

※ビルドコマンドは `hugo --minify` も利用できますが、正常にビルドできる設定を採用しています。

Cloudflare Pagesの「Deployments」画面で最新のデプロイが成功していれば、公開サイトに反映されています。

> **クリス**：`HUGO_VERSION` はなぜ指定するんですか？
>
> **タマキ先生**：指定しないと、Cloudflare側の既定のバージョンでビルドされるんだ。それが手元のHugoやPaperModが求めるバージョンより古いと、ローカルでは表示できるのに本番のビルドだけ失敗する、ということが起こる。**手元と本番のバージョンを揃える**ための設定だね。

### HugoとCloudflare Pagesの役割の違い

HugoはWebサイトを生成するツールで、Cloudflare Pagesは生成されたWebサイトをインターネットへ配信するサービスです。

つまり、Hugoそのものがインターネット上で常時稼働しているわけではありません。Pushのたびに、Cloudflareのビルド環境でHugoが実行され、生成されたHTMLなどの静的ファイルが配信されています。

> **クリス**：Hugoはずっと動いているサーバーだと思っていました。
>
> **タマキ先生**：Hugoは「工場」で、Cloudflare Pagesは「お店」みたいなもの。工場はPushのたびに一度だけ動いて商品（HTML）を作り、お店はその商品を並べて配っているんだよ。

## 9. 次回からの記事公開手順

今後の記事作成では、次の手順だけ覚えておけば問題ありません。

```powershell
# 1. ブログのディレクトリへ移動
cd $HOME\Documents\shun-tech-blog

# 2. 新しい記事を作成
hugo new content content/posts/new-article.md

# 3. Markdownファイルを編集・保存（draft: false を確認）

# 4. 変更確認
git status

# 5. 記事を登録
git add content/posts/new-article.md

# 6. 変更履歴を記録
git commit -m "docs: add new article"

# 7. GitHubへアップロード
git push
```

既存記事の修正であれば、記事作成コマンドは不要です。Markdownを修正して保存したあと、`git add`、`git commit`、`git push` を実行するだけです。

## 10. セキュリティについて

このブログは誰でもアクセスできる公開サイトで、GitHubのリポジトリもPublicで運用しています。つまり、記事だけでなく、GitHub上のソースコードや**変更履歴**も第三者が閲覧できます。

特に、次の情報は公開しないようにします。

- 顧客名・社内システム名
- 実際のIPアドレスやホスト名
- アカウント名・パスワード
- APIキーやアクセストークン
- 社内ネットワークの詳細な構成
- 非公開の設定情報やログ

また、GitHubとCloudflareのアカウントには二要素認証を設定し、不正アクセス対策を行います。静的サイトであっても、アカウントが乗っ取られるとWebサイトを書き換えられる可能性があります。

> **クリス**：もし間違って機密情報を公開しちゃったら、記事を直してPushし直せば大丈夫ですか？
>
> **タマキ先生**：記事からは消えるけど、**Gitの履歴には残る**んだ。Publicリポジトリなら、過去のコミットをたどれば誰でも見られてしまう。パスワードやAPIキーなら、すぐに無効化して新しいものに変えるのが先。だからこそ、Pushする前の確認がいちばん大事なんだよ。

## 11. 今後の運用方針

まずは複雑な機能を追加せず、技術記事を継続的に投稿することを優先します。主なテーマは次を想定しています。

- AWSの運用・トラブルシューティング
- Azureの設計・構築・運用
- Windows Server
- ネットワーク
- PowerShell
- Infrastructure as Code（IaC）
- クラウド運用改善

将来的には、GitHub Actionsを利用した記事チェックや、ChatGPTによるMarkdown作成支援などの自動化も検討します。ただし、自動化を目的にするのではなく、技術情報を継続的に蓄積することを重視します。

## まとめ

Hugo・GitHub・Cloudflare Pagesを組み合わせて技術ブログを構築しました。自分のPCでMarkdownの記事を作成し、GitHubへPushするだけで、自動的にWebサイトへ反映されます。

ブログを始めた目的は、日々の技術経験を記録して自分の知識として蓄積するとともに、将来のキャリア形成にも活用することです。

**記事を書く → GitHubにPushする → Cloudflare Pagesが自動公開する**

> **クリス**：仕組みはシンプルなのに、Git、ビルド、デプロイ、セキュリティと、いろいろな要素が詰まっているんですね。
>
> **タマキ先生**：そう。そして一番大事なのは、仕組みより**書き続けること**。このシンプルな運用を基本に、少しずつ記事を増やしていこう。
