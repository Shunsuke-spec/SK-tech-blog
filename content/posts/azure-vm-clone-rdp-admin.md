Azure上のWindows Serverを複製し、ドメイン離脱・コンピュータ名変更を行ったところ、再起動後にPingが通らず、通常のRDP接続もできなくなりました。一見「サーバが起動していない」ように見えましたが、実際はサーバは起動しており、原因は**RDSライセンスエラー**でした。

切り分けの流れを、2人の会話をはさみながらまとめます。

**登場人物**

- **クリス**：インフラを勉強中の質問役
- **タマキ先生**：やさしく答えてくれる回答役

## この記事でわかること

- Pingが通らなくても、サーバが停止しているとは限らない理由
- `Test-NetConnection` で「ネットワークの問題か、サーバ側の問題か」を切り分ける方法
- RDSライセンスエラーが出たときに `mstsc /admin` で入れる理由
- 複製・ドメイン離脱でライセンスエラーが出た、考えられる原因と確認方法

---

## 1. やったこと：複製・ドメイン離脱・名前変更

今回の作業の流れは次のとおりです。

1. ドメイン参加済みのサーバを停止
2. Azure上でVMを複製
3. 複製したサーバはDNS未設定のまま起動
4. 複製サーバをドメインから離脱
5. 複製元とのドメイン上の競合を避けるため、コンピュータ名を変更
6. 再起動

再起動後、Azureポータル上の状態は「実行中」。しかし、Pingは通らず、通常のRDP接続も失敗しました。

> **クリス**：ポータルでは動いているのに、PingもRDPもダメ。これはOSが起動に失敗しているんじゃないですか？
>
> **タマキ先生**：そう見えるよね。でも、PingとRDPはまったく別の仕組みで動いているんだ。両方失敗していても、原因が同じとは限らないよ。

## 2. 最初に疑ったこと

この時点で疑ったのは、次のあたりです。

- Azure NSGの許可設定
- Windowsファイアウォール
- OS内のNIC・IP設定
- DNS未設定によるドメイン関連の不整合
- ドメイン離脱後のログインユーザーの問題

> **クリス**：候補が多すぎて、どこから見ればいいかわかりません。
>
> **タマキ先生**：複製・ドメイン離脱・名前変更を一度にやると、ドメイン、DNS、ファイアウォール、RDPが全部怪しく見えるんだよね。だからこそ、一つずつ順番に切り分けるのが大事なんだ。

## 3. Pingが通らない＝サーバ停止、ではない

まず押さえておきたいのは、**Windows Serverは、ファイアウォールでICMP（Ping）が拒否されていれば、OSが正常に動いていてもPingに応答しない**ということです。

特にドメイン離脱後は、Windowsファイアウォールの**ネットワークプロファイル**が「ドメイン」から「パブリック」や「プライベート」に変わることがあります。ドメインプロファイルではPingを許可していても、プロファイルが変わった結果、Pingが拒否されるようになる、ということが起こりえます。

> **クリス**：ドメインを抜けると、ファイアウォールのルールまで変わるんですか？
>
> **タマキ先生**：ルール自体は変わらないけど、**どのプロファイルのルールが適用されるか**が変わるんだ。ドメインプロファイルでだけPingを許可していたなら、パブリックに変わった時点でPingは止まる。サーバが落ちたわけじゃないんだよ。

## 4. 3389番ポートは応答していた

そこで、PingではなくRDPが使う**3389番ポート**に直接TCP接続できるかを確認しました。

```powershell
Test-NetConnection <対象サーバのIPアドレス> -Port 3389
```

結果は `TcpTestSucceeded : True` でした。

> **クリス**：これで何がわかるんですか？
>
> **タマキ先生**：3389番ポートまでTCPの接続が成立した、ということだね。つまり、こういう状態だとわかる。
>
> - VMは起動している
> - 対象のIPまで経路がある
> - NSGもWindowsファイアウォールも、3389は通している
> - RDPのサービスも応答している
>
> **クリス**：じゃあ、ネットワークの問題ではない？
>
> **タマキ先生**：そう。問題は「通信が届かない」ことではなく、**届いたあとの認証やセッション確立の段階**に絞れたんだ。

## 5. エラーメッセージを読む：RDSライセンスエラー

改めて通常のRDPで接続すると、次のエラーが表示されていました。

```text
ライセンスを提供するためのリモート デスクトップ ライセンス サーバーがないため、
リモート セッションは切断されました。
```

これは、通常のRDP接続が**RDS（リモートデスクトップサービス）の利用者セッション**として扱われ、ライセンスを確認できなかったために切断された、という意味です。

> **クリス**：「接続できない」じゃなくて「接続したけど切断された」なんですね。
>
> **タマキ先生**：そこが大事なところ。ポートの疎通には問題がなくて、**ライセンスの判定で弾かれていた**んだ。「つながらない」で止まらずにエラーの文言を読むと、一気に原因に近づけるよ。

## 6. 解決：管理用セッションで接続する

通常のRDPではなく、管理用セッションを指定して接続しました。

```powershell
mstsc /admin /v:<対象サーバのIPアドレス>
```

これでログインできました。

> **クリス**：`/admin` って、管理者ユーザーで入るという意味ですか？
>
> **タマキ先生**：よくある勘違いだけど、ユーザー名とは関係ないんだ。`/admin` は**サーバ管理用のセッションとして接続する**オプション。管理用セッションはRDSのライセンス確認の対象外なので、ライセンスエラーを回避して入れるんだよ。

## 7. ログインユーザーの注意点

ドメイン離脱後は、ドメインユーザーではなく**ローカルユーザー**でログインする必要があります。ユーザー名は次の形式で指定します。

```text
.\ローカルユーザー名
```

`.\` は「接続先サーバ自身のローカルユーザー」という意味です。ドメイン離脱後でも、ローカル管理者アカウントが有効であればログインできます。

再びドメインに参加させたあと、ドメインユーザーでログインしたい場合も、通常のRDPでは同じライセンスエラーになる可能性があります。その場合も `mstsc /admin` で接続し、資格情報の画面で次のどちらかの形式で指定します。

```text
ドメイン名\ユーザー名
ユーザー名@ドメイン名
```

> **クリス**：ローカル管理者のパスワード、覚えていないとまずいですね。
>
> **タマキ先生**：そう。ドメインを抜ける作業の前に、ローカル管理者で入れることを確認しておくのが安全だよ。抜けたあとに入れないと、Azureのシリアルコンソールやパスワードリセット機能に頼ることになるからね。

## 8. 考えられる原因（推定）

ここまでで「何が起きていたか」はわかりましたが、**なぜ複製後にライセンスエラーが出るようになったのか**は、まだ確定できていません。状況から考えられる原因を挙げておきます。

### 前提：このサーバにはRDSHの役割が入っていた

このエラーが出るのは、**リモートデスクトップ セッションホスト（RDSH）**の役割がインストールされているサーバです。RDSHが入っていると、複数ユーザーの同時接続ができる代わりに、RDS CAL（ライセンス）の確認が行われます。役割がなければ、管理用の同時2セッションまではライセンスなしで使えるので、このエラーは出ません。

つまり、複製元のサーバにもRDSHが入っていて、複製元では**何らかの形でライセンスが確認できていた**、と考えられます。

### 原因候補1：ライセンスサーバの設定がドメインから配られていた（最有力）

ライセンスサーバの場所やライセンスモードは、**グループポリシー（GPO）**で配布するのが一般的です。もし複製元がドメインのGPOでライセンスサーバの設定を受け取っていたなら、

- ドメインを離脱したことでGPOの設定が適用されなくなった
- DNSが未設定なので、仮に設定が残っていてもライセンスサーバの名前を解決できない

のどちらか、または両方で、ライセンスサーバが見つからなくなった可能性があります。今回の作業内容（DNS未設定・ドメイン離脱）と一番よく合うのがこれです。

### 原因候補2：猶予期間が切れていた

RDSHは、役割を入れてから一定期間（猶予期間）はライセンスサーバなしでも利用できます。複製元が猶予期間で動いていた場合、その経過状態は複製先にも引き継がれます。たまたま期限が切れたタイミングだった、という可能性もあります。

### 原因候補3：ライセンスモードとドメイン離脱の組み合わせ

ライセンスモードが**ユーザー単位（Per User）**の場合、ライセンスの管理はActive Directoryと結びついています。ワークグループ状態のサーバでは想定どおりに動かないことがあり、ドメイン離脱そのものが影響した可能性もあります。

> **クリス**：複製前は普通に入れていたのに、なんで、と思っていました。
>
> **タマキ先生**：複製したVMは、役割の設定も猶予期間の経過も、元のサーバの状態をそのまま引き継ぐ。それに、複製後は別のネットワークやドメインから切り離された状態で動かすことが多いから、元のサーバでは見えていたライセンスサーバが、複製先からは見えなくなるんだ。**「元と同じもの」が「元と同じ環境」で動いているとは限らない**、というのが複製の落とし穴だね。

### 原因を確かめるには

管理用セッションで入れたら、次のコマンドで状態を確認できます。

```powershell
# RDSHとライセンス関連の役割が入っているか
Get-WindowsFeature RDS-RD-Server, RDS-Licensing

# GPOでライセンスサーバ・ライセンスモードが指定されているか
Get-ItemProperty "HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" -ErrorAction SilentlyContinue |
    Select-Object LicenseServers, LicensingMode

# 猶予期間の残り日数
$ts = Get-CimInstance -Namespace root/cimv2/TerminalServices -ClassName Win32_TerminalServiceSetting
Invoke-CimMethod -InputObject $ts -MethodName GetGracePeriodDays
```

GUIで確認したい場合は、RDSHのサーバで **RD ライセンス診断ツール**（`lsdiag.msc`）を開くと、ライセンスサーバとライセンスモードの状態、問題点をまとめて表示してくれます。

## 9. 根本対応：`/admin` は回避策

`/admin` で入れたのは、あくまで**管理者が入れるようになった**だけです。一般ユーザーは通常のRDPで入るので、引き続きエラーになります。サーバの用途に応じて、根本対応をしておく必要があります。

- **RDSHが不要なサーバの場合**：RDSHの役割を削除する。管理目的のRDP（同時2セッションまで）なら、役割がなくても使えます
- **RDSHが必要なサーバの場合**：ドメインへ再参加・DNSを設定したうえで、ライセンスサーバとライセンスモードが正しく適用されているかを確認する

> **クリス**：入れたから解決、じゃないんですね。
>
> **タマキ先生**：そう。`/admin` は「入口を確保する手段」で、ゴールは原因を取り除くこと。複製したサーバは、元のサーバから何を引き継いでいて、何を失ったのかを一度見直しておくと安心だよ。

## 10. 確認に使ったコマンド

```powershell
# RDPポートの疎通確認
Test-NetConnection <対象サーバのIPアドレス> -Port 3389

# 管理用セッションでのRDP接続
mstsc /admin /v:<対象サーバのIPアドレス>

# ドメイン参加状態の確認
(Get-CimInstance Win32_ComputerSystem) | Select-Object Domain, PartOfDomain

# ネットワークプロファイルの確認
Get-NetConnectionProfile

# Windowsファイアウォールのプロファイル確認
Get-NetFirewallProfile

# RDS関連の役割の確認
Get-WindowsFeature RDS-RD-Server, RDS-Licensing
```

ドメイン参加状態は `wmic computersystem get domain,partofdomain` でも確認できますが、`wmic` は新しいWindowsでは非推奨・削除が進んでいるため、`Get-CimInstance` を使う方が確実です。

## 11. まとめ

| 確認したこと | 結果 | わかったこと |
|---|---|---|
| Azureポータルの状態 | 実行中 | VMは起動している |
| Ping | 失敗 | ドメイン離脱でファイアウォールのプロファイルが変わり、ICMPが拒否された可能性 |
| `Test-NetConnection -Port 3389` | 成功 | ネットワーク経路・NSG・ファイアウォール・RDPサービスは問題なし |
| 通常のRDP接続 | ライセンスエラー | RDSライセンスサーバが見つからず、セッションが切断された |
| `mstsc /admin` | 成功 | 管理用セッションはライセンス確認の対象外 |

切り分けの順番としては、次の流れが有効でした。

1. Azureポータル上でVMが実行中か確認
2. Pingではなく3389番ポートを確認
3. 通常RDPのエラー内容を確認
4. RDSライセンスエラーなら `mstsc /admin` を試す
5. ローカルユーザーまたはドメインユーザーでログインを確認
6. 入れたら、ライセンス設定を確認して根本対応する

> **クリス**：Pingが通らないだけで「サーバが止まってる」と決めつけちゃいけないんですね。
>
> **タマキ先生**：そう。ネットワークの問題か、サーバ側の問題かを、ポート単位で順番に切り分けていく。そしてエラーメッセージをちゃんと読む。この2つを習慣にしておくと、トラブル対応がぐっと速くなるよ。
